# Proposal — P0 Foundation (Feed Dealer ERPNext)

## Why

The `app_cam` repo contained only planning documents (`.plan/`) and OpenSpec scaffolding — there was no `feed_dealer` custom app. Every later phase (P0.5 migration, P1A–P1G business logic, P2/P4 mobile clients) depends on a site that already owns the core DocTypes, roles and permission model. Without that foundation, P1 logic would be written against DocTypes that do not exist or that get redesigned mid-flight, breaking the "Batch Debt is allocation-only" invariant that the whole data model rests on.

**The runtime target is the user's own ERPNext site, not a stack built by this repo.** ERPNext is already installed and running on the user's Mac mini via `frappe_docker`, and is reached from this machine two ways:

- an ngrok HTTPS endpoint with API token auth (`.env`: `ERPNEXT_URL`, `ERPNEXT_API_KEY`, `ERPNEXT_API_SECRET`) for REST reads/writes;
- an MCP bridge over Tailscale that can run `docker exec` / `bench` on that machine, which is what makes `bench migrate` and `bench execute` possible at all.

**The site runs ERPNext v16, not the v15 the plan was written against.** v16 differs where it matters for this change: the `UOM` DocType no longer carries `conversion_factor` (conversions moved to the `UOM Conversion Factor` DocType, which additionally requires `category`), and string-typed SQL functions are rejected in `SELECT` fields. P0 targets the site that actually exists.

## What Changes

- **No Docker stack is added to this repo.** An earlier draft of this change built a local Compose stack; it was removed. The runtime belongs to the Mac; deploying the app is a bind mount plus `bench migrate`, and the app source under `apps/feed_dealer` is the only durable artifact here.
- Create the custom app `feed_dealer` with module **Feed Dealer** (generated by `bench new-app`, not hand-invented) and install it on the target site.
- Seed baseline masters — UOM (`Bao`/`Tấn`/`Kg`), Item Groups (Cám lợn/gà/cá, Thuốc thú y), Customer Groups (Trại lớn/vừa, Hộ nhỏ, Đại lý cấp 2), Price Lists (Giá sỉ, Giá lẻ), and the default Company/Warehouse settings — all by **name lookup**, create-if-absent, never overwriting what an operator already configured.
- Create roles: `Feed Dealer Manager`, `Feed Dealer Staff`, `Feed Driver`, `Feed Farmer` (+ read-only posture for the later AI role).
- Define 19 DocTypes (JSON metadata + Python controller + permissions) under module **Feed Dealer**: `Feed Dealer Settings` (Single), `Feed Batch`, `Batch Debt`, `Payment Allocation`, `Credit Score`, `Collateral`, `Action Item`, `Data Processing Consent`, `Debt Confirmation Slip`, `Batch Operation`, `Sales Return Request`, `AI Workflow Config`, `E-Invoice Log`, and the child tables they reference.
- **Rename the lứa nuôi DocType from `Batch` to `Feed Batch`.** A DocType name is global across apps, so shipping `Batch` overwrote ERPNext's own stock `Batch` metadata (its module flipped from `Stock` to `Feed Dealer`) and broke stock code. `Feed Batch` keeps the plan's user-facing batch code (`LOT-2026-00001`).
- Enforce the two P0 hard constraints at the DocType level:
  - `Batch Debt` is an **allocation layer only** — `paid_amount`, `returned_amount`, `outstanding_amount`, `status`, `overdue_days`, `late_payment_fee` are read-only/derived.
  - `Batch Debt.sales_invoice` is `reqd=0` with `mandatory_depends_on` so it is required only when `is_opening_balance = 0` (opening-balance debts carry `opening_journal_entry` instead).
- Register the `hooks.py` skeleton for `Sales Invoice`, `Payment Entry` and `Feed Batch` with P1 TODO bodies.
- Publish acceptance evidence as an executable script, not prose: DocTypes installed under the app, derived fields read-only, opening-balance debt creates with `sales_invoice` null, non-opening debt without invoice is rejected, a Farmer cannot read another customer's Feed Batch, settings persist the interest rate, the hook surface is registered and callable, no non-manager role can write financial DocTypes, and the seeded masters exist.

**Non-goals (explicitly out of P0):** real payment allocation / credit-limit / rebate / e-invoice / cascade logic, mobile apps, n8n/AI wiring, real data import (P0.5), and any change to the ERPNext installation itself. Nothing in P0 writes financial truth beyond schema plus derived-field stubs.

## Capabilities

### New Capabilities

- `platform-runtime`: the contract for running `feed_dealer` on the user's existing ERPNext v16 site — the app reaches the bench as a bind-mounted custom app, the site answers over HTTPS, an authenticated API call identifies `Administrator`, and `bench migrate` is clean and re-runnable.
- `dealer-masters-and-roles`: baseline master data (UOM/Item Group/Customer Group/Price List/Company/Warehouse) created by name-lookup, plus the four feed-dealer roles and their permission posture.
- `feed-dealer-data-model`: the core DocType contract — required fields, read-only derived fields on `Batch Debt`, the opening-balance vs invoice-linked rule, audit tracking on financial DocTypes, the Single settings DocType, and the hook registration surface for later phases.

### Modified Capabilities

None — `openspec/specs/` is empty; this change introduces the first capabilities.

## Impact

- **New code:** `apps/feed_dealer/**` — app package, 19 DocTypes with controllers, `hooks.py` event surface, master-seed module, migrate patch, and the acceptance script.
- **Bootstrap tooling (not shipped):** `.agent/` holds the local scripts used to reach the Mac (`mcp_client.py`, `bench.py`, `mac.py`, `push_to_mac.py`) and to generate the DocType JSON (`gen_feed_dealer.py`). These are development aids, deliberately outside `apps/`.
- **External runtime:** the existing ERPNext v16 site on the Mac (`frappe` 16.17.2 / `erpnext` 16.16.0), which already hosts other apps — `camvlxd`, `custom_app` — and real data (3 companies, existing UOMs and warehouses). P0 must not disturb them.
- **Downstream:** unblocks P0.5 (data migration), P1A (order → batch debt allocation), P1B (payment allocation) and the P2/P4 clients, all of which read these DocTypes.
- **Secrets:** the site URL and API key/secret live in an untracked `.env`; no credential is committed, and only variable *names* are referenced in docs.
