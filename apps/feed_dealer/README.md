# feed_dealer

ERPNext custom app for the feed dealer system (đại lý cám): batch-based debt
tracking, credit limits, AI-assisted actions.

**Phase P0 (this app as it stands) = schema only.** All DocTypes, roles,
permission posture and hook registrations are final; business logic is
deliberately stubbed for Phase 1. Nothing here writes financial truth yet.

## Layout (read this before adding a DocType)

```
apps/feed_dealer/
  pyproject.toml
  feed_dealer/                     <- Python package (hooks.py, patches, setup)
    hooks.py
    modules.txt                    ("Feed Dealer")
    patches.txt
    patches/v0_0_1/seed_masters.py
    events/                        sales_invoice.py, payment_entry.py, batch.py
    setup/                         masters.py, p0_acceptance.py
    feed_dealer/                   <- MODULE DIR = scrub("Feed Dealer")
      doctype/<scrub(name)>/
        <scrub(name)>.json         DocType metadata
        <scrub(name)>.py           controller - REQUIRED for EVERY DocType,
                                   child tables included
        __init__.py                MANDATORY
```

The triple nesting (`feed_dealer/feed_dealer/feed_dealer/`) is Frappe's
convention, not a mistake: the first is the app root, the second is the Python
package, the third is the module folder named after `modules.txt`. The
`__init__.py` inside the module folder is **mandatory** — without it Python
treats the folder as a namespace package, `__file__` is `None`, and
`frappe.get_pymodule_path` computes the wrong DocType path.

A missing controller aborts `migrate` for the DocType *and its parent* (a child
table without a `.py` breaks the parent's sync). And the class name is not
snake_case — Frappe imports `doctype.replace(" ", "").replace("-", "")`, so
`AI Workflow Config` must be `class AIWorkflowConfig`, not `AiWorkflowConfig`.

## Generated DocTypes — do not hand-edit logic

`Feed Batch` and `Batch Debt` carry real controller logic that is **generated**:
`.agent/gen_feed_dealer.py` (outside the app, bootstrap tooling only) holds all 19
DocType specs and writes the JSON plus controllers. Its output is ordinary Frappe
source and is committed.

**Consequence:** editing `batch_debt.py` or `feed_batch.py` directly loses the
change the next time the generator runs. Edit the spec in the generator and
regenerate; only the DocTypes without business logic are safe to touch in place.

## Non-obvious decisions

* **The lứa nuôi DocType is `Feed Batch`, not `Batch`.** A DocType name is global
  across apps, so shipping `Batch` overwrote ERPNext's own stock `Batch`
  (its module flipped `Stock` → `Feed Dealer`) and broke stock code with
  `'Batch' object has no attribute 'reference_doctype'`. The rename is the fix;
  the plan's user-facing batch code is preserved as the document name
  (`autoname: format:LOT-{YYYY}-{#####}`, e.g. `LOT-2026-00638`). Before adding a
  DocType, check its name against `frappe` and `erpnext` — this bit once.
* **`Batch Debt` is an allocation layer.** `paid_amount`, `returned_amount`,
  `outstanding_amount`, `status`, `overdue_days` and `late_payment_fee` are
  `read_only` in metadata *and* recomputed by the controller, because `read_only`
  is a UI hint that programmatic writes ignore.
* **`sales_invoice` is `reqd=0`.** The "required unless opening balance" rule is
  enforced in `BatchDebt.validate()`, not by `mandatory_depends_on`, because the
  metadata rule is client-side and any API/import path bypasses it.
* **`opening_journal_entry` is not enforced in P0.** Opening-balance debts must
  be creatable with an empty `sales_invoice`; the journal entry is created by the
  P0.5 migration boundary, which is where enforcing it makes sense.
* **No Company is created by the seeder.** The site has real companies; adding
  one would fork the chart of accounts. The seeder verifies a VND company exists
  and reuses an existing feed warehouse when it can find one.
* **`Sales Return Request.linked_outbreak_alert` is deferred.** `Outbreak Alert`
  is not a P0 DocType, so the link would dangle. It lands with the outbreak work.
* **Master seeder is a patch, not fixtures** — fixtures overwrite operator edits
  on every migrate.

## ERPNext v16 gotchas (each one cost a real failure)

* **UOM conversions moved.** `UOM` has no `conversion_factor`/`reference_uom` any
  more; conversions live in `UOM Conversion Factor`, whose `category` is
  **required** (`MandatoryError: [UOM Conversion Factor, …]: category`).
* **SQL functions are banned in string `fields`.** `fields=["sum(x) as total"]`
  raises `SQL functions are not allowed as strings in SELECT`; use
  `fields=[{"SUM": "x", "as": "total"}]` — the allowed keys are in Frappe's
  `FUNCTION_MAPPING`.
* **`doc.owner = user` before `insert()` does not stick** — Frappe overwrites it
  with the session user. Assign ownership with `db_set("owner", …)` afterwards.
* **Deleting a submitted doc needs a cancel first.** `force=True` no longer
  bypasses `check_permission_and_not_submitted`.
* **`frappe.get_hooks("doc_events")` values can be lists** once more than one app
  registers the same event (this site's `custom_app` does), not just a string.
* **`bench execute` masks real errors.** It catches the target's exception and
  falls back to `eval(method)`, which surfaces as `NameError: name 'feed_dealer'
  is not defined`. When a run fails, use
  `feed_dealer.setup.p0_acceptance.debug` — it prints every check's real
  traceback and never raises.
